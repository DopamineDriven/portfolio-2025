# Preliminary Findings — Markdown Rendering Regression (apps/web)

**Date:** 2026-07-26
**Branch:** `development` (uncommitted working tree on top of `d61237d`)
**Symptoms observed** (Google Analytics with Next.js post):

1. Inline code spans (e.g. `` `@types/gtag.js` ``) render with a leading line number ("1"), a dark code-block background, and extra left padding — as if they were one-line code blocks.
2. Backtick pseudo-element quotes (`` ` ``) are visible around inline code despite the `prose-quoteless` workup in `global.css`.
3. (Secondary, visible in the same screenshot) Section headings render dim and underlined.

---

## Root Cause 1 — Inline code is now Shiki-highlighted and inherits block-code CSS

**The regression was introduced by the new `prettyCodeOptions` in `apps/web/src/lib/processor-opts.ts:222`:**

```ts
defaultLang: { block: "markdown", inline: "markdown" },
bypassInlineCode: false,
```

The pre-refactor pipeline (`git show HEAD:apps/web/src/lib/mdx-processor.tsx`) passed **no `defaultLang`** to `rehype-pretty-code`. In rehype-pretty-code v0.14.5, inline code without a `{:lang}` meta suffix is *skipped* when there is no inline default language. Setting `defaultLang.inline = "markdown"` opts **every** inline code span into full Shiki highlighting.

Verified by running the actual pipeline (unified + remark-parse + remark-gfm + remark-rehype + rehype-pretty-code@0.14.5 + rehype-stringify) against `` Install `@types/gtag.js` as a dev dependency: ``:

**New options (current working tree):**

```html
<p>Install <span data-rehype-pretty-code-figure=""><code data-language="markdown"
  data-theme="dark-plus" style="background-color:#1E1E1E;color:#D4D4D4"><span
  data-line=""><span style="color:#D4D4D4">@types/gtag.js</span></span></code></span> …</p>
```

**Old options (HEAD):**

```html
<p>Install <code>@types/gtag.js</code> …</p>
```

The new inline output contains a `<span data-line>` child inside `<code>`, which collides with the block-code CSS in `apps/web/src/app/global.css`:

- `global.css:398` — `code { counter-reset: line; … }`
- `global.css:403` — `code > [data-line] { padding-left: 0.25rem; border-left: … }`
- `global.css:408` — `code > [data-line]::before { counter-increment: line; content: counter(line); display: inline-block; width: 1rem; margin-right: 0.5rem; … }`

These selectors were written for fenced blocks but match **any** `code` element with `[data-line]` children — which now includes every inline snippet. That is the literal "1" in the screenshot.

The dark box comes from `keepBackground: true`: rehype-pretty-code copies Shiki's `style="background-color:#1E1E1E"` onto the inline `<code>` element (`node_modules/rehype-pretty-code/dist/index.js`, `apply()` with `inline: true`). Being an inline style, it defeats `.prose code { background-color: transparent }` (`global.css:439`).

Note: `bypassInlineCode: false` is the library default and is not itself a change; the functional change is `defaultLang.inline`.

**Corroboration from the reference implementation (slipstream):** `~/cloneathon/t3-chat-clone/apps/web/src/lib/processor-opts.ts` uses the *identical* `prettyCodeOptions` (including `defaultLang.inline: "markdown"`), yet has no numbering problem, because its `globals.css` sets `code > [data-line]::before { … display: none; }` (line numbers disabled entirely) — so highlighted inline code never receives a counter. The portfolio kept `display: inline-block`, so both blocks *and* inline code get numbered.

## Root Cause 2 — Backticks come from `@tailwindcss/typography`; `prose-quoteless` is never applied

The visible backticks are generated by the typography plugin (`node_modules/@tailwindcss/typography/src/styles.js:1546`):

```js
'code::before': { content: '"`"' },
'code::after':  { content: '"`"' },
```

This fires because the article wrappers opt into prose styling:

- `apps/web/src/ui/post/index.tsx:83` — `className="prose-sm sm:prose text-foreground! …"`
- `apps/web/src/ui/project/index.tsx:83` — `className="prose-sm sm:prose …"`

The counter-measure exists in two generations, and **neither is active**:

1. **Old (deleted) `tailwind.config.ts`** defined the typography modifier `quoteless` (`theme.extend.typography.quoteless.css` with `p code::before { content: none }`, etc.). But activating it requires the `prose-quoteless` class on the wrapper — and `git show HEAD:apps/web/src/ui/post/index.tsx` shows the class was **never in the markup** (`prose-sm sm:prose dark:prose-invert …`), and `git log -S "prose-quoteless"` finds no commit that ever applied it.
2. **New `@utility prose-quoteless`** (`global.css:283`) faithfully ports those selectors to v4 syntax. It is well-formed — but in Tailwind v4 an `@utility` is only *emitted* when the class is used in scanned source, and no file in `apps/web/src` uses `prose-quoteless`. The utility is currently dead code in both senses: never emitted, never matched.

(If it were applied, the selectors would still work against the new inline structure — `& :is(p, li) code::before` matches `p > span[data-rehype-pretty-code-figure] > code` via descendant combinator.)

## Assessment of the "drop the TW prose/forms plugins" hypothesis

**Confirmed as the sound direction.** Evidence:

- The slipstream reference app (`t3-chat-clone/apps/web`) runs the same processor, same pretty-code options, and same custom component map with **no** `@tailwindcss/typography` and **no** `@tailwindcss/forms` — only `tailwindcss-motion`. Every element the typography plugin would style (`p`, `li`, `ol`, `ul`, `blockquote`, `table`, headings, `code` via `CodeBlock`) is already explicitly styled by the rehype-react component map in `mdx-processor.tsx` — the prose layer is a second, competing styling system fighting the first.
- `prose*` classes appear in exactly two files (`ui/post/index.tsx:83`, `ui/project/index.tsx:83`). Nothing else in `apps/web/src` references prose.
- `@tailwindcss/forms` is pure liability: **zero** `<input>`, `<textarea>`, `<select>`, or `form-*` class usage anywhere in `apps/web/src`. It only injects global base styles that can bleed into other UI.
- Removing typography also removes: the backtick pseudo-elements (Root Cause 2 disappears without needing `prose-quoteless` at all), the `.prose a` link-color/underline bleed into headings (see Secondary Finding B), and the need for the `.prose`/`.dark .prose` override blocks in `global.css:429–482`.

**Removal blast radius to account for:**

- `global.css` rules that become dead and should go with it: `.prose { max-width: none }`, `.prose pre`, `.prose code`, `.prose a`, `.prose h1–h6`, `.dark .prose *`, `.prose p/ul/ol` (lines 429–482), plus the `@utility prose-quoteless` block (283–292).
- The wrappers in `post/index.tsx` / `project/index.tsx` lose prose's typographic scale (`prose-sm sm:prose` was providing base font-size/margins). Body text color/size is already handled by the wrapper (`text-sm sm:text-base`, `text-foreground!`) and the component map (`p` gets `mb-1.5 leading-7`), so the gap is small, but spot-check headings/margins after removal. The `[&>p]:prose-p:text-pretty` variant also dies with the plugin.
- Inline code will then have *no* styling at all unless the pipeline highlights it (which the new `defaultLang.inline` does — slipstream's model) or a `code:not([data-rehype-pretty-code-figure] code)` rule is added (slipstream has one at `globals.css:622`).

## Decision points for the fix (pending)

1. **Line numbers on inline code:** either scope the counter CSS to blocks — `figure[data-rehype-pretty-code-figure] code > [data-line]::before` or `pre code > [data-line]::before` — or follow slipstream and set `display: none` (slipstream shows no line numbers via CSS at all). Scoping to `pre code` preserves the current block-code numbering seen in the screenshot.
2. **Inline background:** decide whether to keep Shiki's `#1E1E1E` inline background (`keepBackground: true`) for inline code or neutralize it; slipstream keeps it and styles inline code via the `:not(figure… code)` selector.
3. **Plugin removal:** drop `@plugin "@tailwindcss/typography"` and `@plugin "@tailwindcss/forms"` from `global.css`, strip `prose*` classes from the two wrappers, delete the dead `.prose` rule blocks and `@utility prose-quoteless`.

## Secondary findings (same working tree, adjacent breakage)

These are not the reported bug but were surfaced during the sweep and affect the same screenshot/pages:

- **A. `dark:` variant is dead app-wide.** `global.css:12` defines `@custom-variant dark (&:where([data-theme=dark], …))`, but the theme is applied as a *class*: `layout.tsx:115` uses `next-themes` `ThemeProvider attribute="class"` and the flash-prevention script does `document.documentElement.classList.add('dark')` (`layout.tsx:105`). Nothing sets `data-theme`. Every `dark:*` utility silently no-ops (the old config used `darkMode: "selector"`, i.e. `.dark`). The plain-CSS `.dark .prose …` overrides in `global.css` still work because they target the class directly.
- **B. Heading text is now nested inside the anchor.** The old `createHeading` rendered an empty `<a class="anchor">` *sibling* followed by the text; the new `apps/web/src/lib/create-heading.ts:21` wraps the heading text **inside** the anchor. Under prose, headings therefore inherit link styling — `.prose a` color (`global.css:445`, muted blue) plus typography's link underline — producing the dim underlined headings in the screenshot. Removing the typography plugin fixes the visual; whether text should live inside the anchor is a separate call (slipstream's `create-heading` should be compared).
- **C. Missing semicolon in `@theme`.** `global.css:139` — `--duration-theme: 0.5s` has no terminating `;`, so the declaration swallows the next line and `--duration-loading` is never defined.
- **D. Orphaned CSS variable.** `body` transition (`global.css:356`) and `.theme-transition` (`global.css:363`) reference `var(--theme-transition-duration)`, but that variable was removed in this refactor (renamed to `--duration-theme`). The transitions now have an invalid duration.
- **E. `highlight.css` re-imports Tailwind layers.** `apps/web/src/app/highlight.css:1-2` imports `tailwindcss/theme.css` and `tailwindcss/utilities.css` even though `global.css:1` already imports all of `tailwindcss`; the file is `@import`ed into `global.css:3`, duplicating those layers in the bundle.
- **F. Pipeline ordering is fine.** `rehypeSanitize` runs *before* `rehypePrettyCode` and the schema allows `data-*`/`className`/`style` on `*`, so sanitization is not stripping pretty-code output. Not a cause.

## Reproduction command (for regression testing the fix)
